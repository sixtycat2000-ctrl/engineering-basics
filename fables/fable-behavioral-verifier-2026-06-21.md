📖 每日工程寓言 — 行为验证器

## 营造司的十二卷营造录

汴京城西有个官办考场，叫营造司大比。

每三年一次，各州县的工匠送来最得意的作品，争夺一个叫"御用匠师"的称号。评判方式从设立之初就没变过：每件作品必须附一份"营造录"——写法、用料、比例、原理，样样写清楚。阅卷官们坐堂评议，从营造录的完备程度来判断一位匠师的真功夫。

字越多，分越高。图越细，越接近榜首。

那年送来一件特别的贡品——一座来自西南边郡铜鼓镇的青铜水钟。水钟的样子不起眼，没有鎏金，没有雕花，甚至齿轮都比正常的水钟少了一半。但营造录上只有一句话：

"此钟一旦启用，百年不差一刻。"

阅卷官们看了，脸色铁青。字最少，分最低。营造录写不满一页，怎么可能是好作品？这座水钟被扔进了杂物房。

大比的魁首是一座来自江南的鎏金自鸣钟。营造录整整十二卷，详细到每个齿轮的齿数、每次摆动的角度、每根轴之间的摩擦力。阅卷官拍案叫绝，当场授匾。魁首的营造录被装裱成册，陈列在营造司大堂，供后来的工匠瞻仰。大家都说，这才是匠人的典范——不仅做得好，更说得清自己为什么做得好。

三年后，江南的那座自鸣钟停了。

不是普通的停。它在某个深夜忽然越走越快，指针追着时间跑，最后齿轮崩裂，铜屑飞溅。营造司的官员们翻出那十二卷营造录，逐个零件核对。图纸上的一切都完美无缺——每个尺寸都精确，每处衔接都合理。按道理，它不该坏。

可它就是坏了。十二卷营造录里，没有一个字能解释这件事。

这时候有人想起了杂物房里的水钟。他们把水钟搬到大堂，试了三天，一刻不差；试了一个月，仍一刻不差；试到第七个月时，有人拿日晷对照——水钟和太阳的误差，没有超过一次呼吸的时间。

传旨官快马赶往铜鼓镇。他找到水钟的匠人——一位满头白发的老妇人，正在河边修一道被山洪冲垮的石坝。

"您的钟全城都在用了，"传旨官气喘吁吁地说，"可您的营造录只有一句话，我们至今不知道它是怎么做到的。"

老妇人头也没抬，在水里摸了摸石缝的位置，说：

"如果你们想知道它准不准，看它就够了。盯着一个摆锤看三天，比我写三十页纸明白得多。"

传旨官站在河边，忽然意识到一件可怕的事：营造司比了这么多年的"大比"，比的从来不是谁的钟走得准——比的是谁的文章写得好。那些精美的营造录，让所有人误以为自己找到了答案，实际上只是找到了一份写得漂亮的说明书。

后来营造司改了一条规矩：所有贡品必须在真实岗位上运行一年，才能参与评分。营造录依然要交，但它不再是评判的依据——只是在事后理解时翻阅的参考。

这条规矩，被后人称作"实考"。

💡 概念解析：行为验证器（Behavioral Verifier）

这则寓言讲的是 DeepSWE benchmark 中最核心的方法论创新——**行为验证器**。

传统的 AI coding agent 评估方式（如 SWE-bench Pro）基于「检查实现」：跑任务现有的测试套件，看代码 diff 是否被正确合并。问题是，现有测试套件可能被污染（gold solution 泄露在 commit history 里）、不覆盖边界条件、或者判断的是"代码看起来对不对"而不是"运行起来对不对"。SWE-bench Pro 的 FP 率（把错的判成对的）高达 8.5%，FN 率（把对的判成错的）高达 24%。

DeepSWE 的做法完全不同。它为每个任务手写独立的行为验证器（behavioral verifier），只检查一件事：**修改后的软件在真实运行中是否表现出期望的行为**。比如，它不检查代码里有没有写 "abort handler"，而是直接模拟网络断开，看连接是否真的被正确中止。验证的是"做了什么"，不是"长什么样"。

结果 FP 率降到 0.3%，FN 率降到 1.1%——几乎消除了误判。

这个原理远不止于 AI 评估。它是软件工程中"测试行为而非实现"这一基础原则的极致应用。在 AI agent 时代，agent 生成的代码可能风格怪异、结构丑陋，但只要它表现出的行为正确，它就是正确的。反之，一个实现可能结构优雅、注释齐全、通过了 code review，却在边界条件下全面崩溃。行为验证器是对"过程崇拜"的终极解毒剂——真金不怕火炼。要看一座桥稳不稳，最好的办法不是读造桥手册，而是把桥建好，然后走上去。
