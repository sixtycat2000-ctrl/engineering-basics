# 算子融合 — 一则寓言

从前，在大陆最繁华的王都，有一间号称"天下第一"的皇家厨房。

厨房里有一百二十位厨师，每人各司其职。张师傅负责切菜，李师傅负责腌制，王师傅负责翻炒，赵师傅负责调味，孙师傅负责摆盘。他们的规矩是铁打的：每完成一步，半成品必须送回中央食材库，贴上标签，等下一位师傅来取。

这套规矩运行了多年，没人觉得有问题。毕竟每位师傅都是各自领域的一把好手，刀工出神入化，火候精准无误。而且厨房的核心是那口大灶——王师傅的翻炒手艺全靠它。灶台的火力，决定了整间厨房的上限。

直到有一天，国王从极北之地请来一位矮人匠师，打造了一口神炉。

神炉的翻炒能力是旧灶台的一百倍。消息传遍王都，全城欢腾。宰相在朝堂上高声宣布："有了神炉，我们的国宴准备时间将缩短到百分之一！"

可一个月后，御膳房总管愁眉苦脸地来到国王面前。

"陛下……国宴的准备时间，只缩短了不到一半。"

"不可能！"国王拍案而起，"神炉明明快了一百倍！是不是王师傅偷懒？"

总管跪在地上，汗如雨下："陛下，王师傅没有偷懒。神炉确实在全力运转。可是……"

"可是什么？"

这时候，一个刚进厨房三个月的年轻学徒站了出来。

他叫阿译，是今年新招的杂役。别人眼里，他只是个跑腿送菜的。

"陛下，请容许我解释。"阿译说，"过去一个月，我每天什么都不做，就站在厨房角落里数数。"

"数什么？"

"数每位师傅真正在干活的时间，和他们走来走去的时间。"

阿译从怀里掏出一本皱巴巴的册子，翻开第一页。

"王师傅翻炒一盘菜，需要半柱香。但他从食材库把腌好的菜端到神炉前，炒完再端回去，需要一柱香。也就是说，神炉哪怕再快十倍、一百倍，王师傅还是要把大部分时间花在走路上面。"

大殿里安静了。

阿译继续翻："我数了所有师傅的时间。一百二十位师傅，真正动手做菜的时间加起来，不到他们总工时的一半。剩下的一半以上，全花在往返食材库的路上了。"

"那神炉呢？"国王追问，"它占厨房多少工作量？"

"王师傅说，翻炒是整道菜最花力气的一步。如果把所有力气加起来算，翻炒占了九成九。但——"阿译顿了顿，"如果算时间，翻炒只占六成。"

"九成九的力气，六成的时间？"

"是的，陛下。力气几乎都花在翻炒上了，但时间有一大半被走路的功夫吃掉了。"

宰相皱起眉头："这和神炉有什么关系？"

阿译合上册子，走到大殿中央，用手指在石板上画了一张图。

"我们的规矩是：每做完一步，半成品必须送回食材库。张师傅切完菜，放进食材库。李师傅去取，腌完，放回去。王师傅去取，炒完，放回去。赵师傅去取，调完味，放回去。孙师傅去取，摆盘上桌。"

"一道菜，食材要在工作台和食材库之间来回五趟。"

他在图上画了五条粗线，每条线代表一趟。

"现在神炉把翻炒的时间压缩到了百分之一。可来回跑腿的时间，一点没变。所以整道菜的时间，只缩短了一半——因为跑腿的时间本来就不受神炉影响。"

国王盯着石板上的图看了很久。

"那你有什么办法？"

阿译擦掉那张图，重新画了一张。

"不要让半成品回食材库。"

"让张师傅切完菜，直接递给旁边的李师傅。李师傅腌完，直接递给王师傅。王师傅放进神炉炒完，直接递给赵师傅调味。赵师傅调完，孙师傅直接摆盘。五个步骤一气呵成，食材只需要离开工作台一次——上桌的时候。"

大殿里鸦雀无声。

老总管第一个跳出来反对："这怎么行！乱了规矩！每位师傅应该各司其职，中间必须经过食材库，这样才能追溯每一步！万一出了问题，怎么查？"

阿译没有反驳，而是反问："总管大人，您说的对，确实需要记录每一步。但记录每一步和把半成品搬来搬去，是两回事。我们可以在每个师傅完成时记一笔账，不用真的把菜搬回仓库。"

他转向国王："陛下，我还有一个请求。要这样做，我需要事先看到整本菜谱——从头到尾所有步骤。如果我只看到一步，我就不知道下一步是谁做、需要什么，就没法安排他们站在一起。但如果我能看到完整的菜谱，我就能提前把相关的师傅安排在相邻的位置，让食材像流水一样淌过去。"

"这……"老总管张了张嘴，"可是我们厨房从来都是一道菜一道菜地做，从来没人一口气看完过整本菜谱。"

"所以我需要一个新的角色，"阿译说，"我不管做菜。我专门负责在厨房开工之前，把整本菜谱读一遍，然后重新安排每位师傅的站位和交接顺序。"

国王沉思良久。

"准了。试三天。"

三天后，国宴的准备时间缩短了三倍。神炉的威力，终于不再被浪费在跑腿上了。

而阿译，后来成了王都最传奇的人物。人们不叫他厨师，也不叫他总管。他们叫他"编译者"——因为他最擅长的不是做菜，而是读懂整本菜谱，重新编排做菜的顺序，让每一步都衔接得严丝合缝，不浪费一秒钟。

有好事者问他："你到底做了什么？"

他笑着说："我只是让每道菜不再反复进出仓库。你看，真正花在翻炒上的力气占九成九，但时间只占六成。那剩下四成的时间去哪了？全花在搬东西上了。把搬东西的趟数从五趟减成一趟，四成就变成了不到一成。就这么简单。"

## 概念解析：算子融合（Operator Fusion）

今天的故事讲的是 ML 编译器优化中最核心的技术——算子融合。

在现代深度学习中，一个神经网络的推理或训练过程由成百上千个"算子"（operator）组成：矩阵乘法、加法、ReLU 激活函数、LayerNorm、Sigmoid……在默认的"即时执行"（eager execution）模式下，每个算子独立运行：从显存（VRAM）读取数据 → 计算 → 写回显存。如果连续三个算子是"加法 → ReLU → Sigmoid"，数据就要在显存和工作单元之间往返三次。

这就像故事里的厨师们：每做完一步就把半成品送回食材库，下一步的厨师再取出来。

2017 年之后，NVIDIA 的 Tensor Core 让矩阵乘法（matmul）的速度提升了 10 倍，但其他操作（归一化、逐元素运算）的速度没变。结果就是：矩阵乘法占了 99.8% 的计算量，却只消耗 61% 的运行时间。剩下的时间全花在了数据搬运上——读写显存。

算子融合的解决思路是：用编译器（如 PyTorch 的 `torch.compile`）先把整个计算流程"捕获"成一张图（graph capture），然后分析哪些相邻的算子可以合并成一个复合算子。"加法 → ReLU → Sigmoid"从三次显存读写变成一次，数据只在显存和工作单元之间走一趟。这也是为什么阿译说"我需要事先看到整本菜谱"——编译器必须看到完整的计算图，才能知道哪些步骤可以合并。

这个看似简单的优化，是现代 ML 编译器带来的最大性能提升来源。一行 `torch.compile(model)` 就能带来 2-4 倍的加速，核心靠的就是算子融合。
