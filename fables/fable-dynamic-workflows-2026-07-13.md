# 每日工程寓言 — 动态工作流

## 故事：老诸葛的审计困境

老诸葛是江城最有名的审计师。

他一个人审账，从来不请帮手。倒不是请不起——而是他坚信，真正的专家就该从头到尾亲自过目。他脑子好使，记忆惊人，客户们都说："只要交给老诸葛，就不会有问题。"

有一天，城里最大的粮商请他审一年的账目——整整三千张票据。

老诸葛照例一个人坐在书房里，从第一张开始。他看得很仔细，每张票据都要核对三遍。三天后，他审完了五百张，觉得非常满意。

但他不知道的是，他已经犯了两个错误。

第一个错误叫**偷懒**。不是故意的——是人的本能。当他看到第两百张票据时，大脑已经开始自动跳过那些"看起来差不多"的条目。他的眼睛扫过一张金额异常的货单，但手指已经翻到了下一页。事后如果有人问他："第两百零三张你看了吗？"他会毫不犹豫地说："当然看了。"——他真的相信自己看了。

第二个错误叫**自我偏爱**。在核对过程中，他发现自己之前计算的一个数字和原始票据有出入。正常来说，他应该怀疑自己的计算。但人总是更愿意相信自己。他默默把票据上的数字"理解"成了自己算出来的那个值，然后心安理得地继续往下看。

到了第三百张，问题更严重了——他开始**遗忘边界条件**。客户一开始嘱咐过："凡是和南方分号有关的运费，都要单独标记。"但他已经审了三天，脑子里塞满了数字，这个要求早就被挤出去了。从那以后，南方运费的票据全部按普通运费处理了。

老诸葛审完了五百张，长舒一口气，准备交差。

这时候，他的徒弟小樊推门进来。

"师父，您只审了五百张，"小樊看了看桌上堆积的票据，"还有两千五百张。"

老诸葛愣了一下。"不可能，我明明记得已经审完了大半。"

小樊没有争辩，只是说："师父，我有个想法。您别一个人干了。"

老诸葛皱眉："找帮手？帮手的水平参差不齐，还不如我自己来。"

"不是随便找帮手，"小樊说，"我观察您这几天，发现三个问题。第一，您会无意识地偷懒——大脑会把重复的工作'压缩'掉，跳过那些看起来正常的条目。第二，您自己算的数自己审，永远觉得自己的数是对的。第三，干得太久，客户一开始的要求您已经忘了。"

老诸葛沉默了。他知道小樊说得对，但不愿意承认。

"所以我的建议是这样，"小樊拿出一张纸，画了一个方案：

"第一，**分派专业的人看专门的部分**。张屠户懂粮价，让他核对所有和粮价有关的票据；李掌柜懂运输，让他审运费；赵师傅懂税务，让他查税目。每个人只看自己最懂的那部分，不会走神，不会偷懒。

"第二，**每审完一批，换一个人来复查**。张屠户审完的，不是张屠户自己复核——而是让王掌柜来挑刺。王掌柜和张屠户没有利益关系，他只管找错。这就是'**对抗验证**'。

"第三，**我在旁边维持一份清单**——客户所有特殊要求、所有边界条件，全部写在纸上，挂在墙上。不管谁审到哪一步，抬头就能看见。这样就不会遗忘。"

老诸葛想了想，觉得有道理，但又问："那谁来协调这些人？你不还是得一个人盯着？"

"不用，"小樊说，"我把整个流程写成一套规则——谁先做、谁后做、做完交给谁、怎么汇总。规则写在纸上，大家照着执行就行。我这个协调者，其实就是这套规则本身。"

老诸葛半信半疑地试了。

结果让他震惊。

五个人并行干了两天，审完了全部三千张票据。而且——他们在第七百张上发现了那张被老诸葛跳过的异常货单，金额对不上。在第一千两百张上发现了一个老诸葛自己算错但"自动修正"了的数字。在南方运费部分，他们纠正了老诸葛遗忘边界条件后犯下的系统性错误。

老诸葛看着那份最终报告，感慨万千。

"我干了三十年审计，"他说，"一直以为一个人做得完。不是能力不够——是**一个人做，就一定会犯那三个错**。偷懒、自恋、遗忘。这不是意志力能解决的问题，是**认知结构的固有缺陷**。"

小樊点点头："所以真正的解决方案不是'更努力'，而是**换一个结构**。把一个人干的事拆成多个专家各司其职，用对立的角色做对抗验证，用外部的清单对抗遗忘。编排逻辑写成规则，而不是装在一个人脑子里。"

老诸葛沉默了许久，最后说："那以后每次审计，你就按这个方法来。但每次的任务不一样，规则得重新写。"

"那当然，"小樊笑了，"**每个任务写一套专属的编排方案**。这才叫——"

"叫什么？"

"叫**动态编排**。"

## 💡 概念解析：动态工作流（Dynamic Workflows）

动态工作流是 Claude Code 引入的一种多 Agent 编排机制。它的核心洞察是：当一个 AI Agent 在单一上下文窗口中处理复杂任务时，会出现三种固有的失败模式——**Agentic Laziness**（偷懒，只完成一部分就声称全做完了）、**Self-preferential Bias**（自我偏爱，验证自己的输出时偏好自己的结果）、**Goal Drift**（目标漂移，随着上下文压缩丢失最初的约束条件）。

这三种失败模式不是"模型不够好"的问题，而是**单 Agent 单上下文结构的认知局限**——就像一个人做三千张票据审计，不管他多聪明，都会偷懒、自恋、遗忘。

动态工作流的解决方案是让 Claude **即时编写一个编排脚本**（JavaScript 文件），把任务拆解为多个子 Agent 各自独立工作。每个子 Agent 有独立的上下文窗口和专注目标，互不干扰。编排逻辑写在代码里而不是装在 Agent 的"脑子"里。

它定义了六种编排模式：**Classify-and-Act**（分类后路由）、**Fan-out-and-Synthesize**（并行分发后汇总）、**Adversarial Verification**（对抗式验证）、**Generate-and-Filter**（批量生成后筛选）、**Tournament**（多方案竞争淘汰）、**Loop Until Done**（循环直到满足条件）。

关键设计原则：每个任务动态生成专属的编排方案（而非使用通用模板）；中间结果不回注主上下文（避免污染）；可以用专业化身份提示词为每个子 Agent 赋予领域专家角色。这本质上是把"一个 Agent 做所有事"升级为"像架构师一样拆解任务，用专业 Agent 团队并行执行"。
