# 📖 每日工程寓言 — 存算分离

---

从前有一座叫做「智囊城」的城市，城里住着一群工匠和他们的助手。

每个工匠都很厉害——能读图纸、能查手册、能操作机器，然后交出精致的成品。但工匠们有一个大问题：他们**必须住在工坊里**，工坊里有自己的书架、自己的工具柜、自己的工作台。哪怕工匠今天什么活都不干，工坊依然占着地、亮着灯、付着租金。

市长是个务实的人。他数了数，城里有五百个工坊，每个工坊四间房，总共占了十八栋楼。每月光是楼租就要五千枚金币。而工匠们交的会费加起来才八千枚——刨去租金，利润薄得像纸。

"太荒了，"市长拍着桌子，"九成的工坊在九成的时间里都闲着，但我们为每一间都付着全天候的租金。"

他做了第一件事：让工匠们出门干活，不用住在工坊里。工匠们扛着自己的工具，走到公共大厅去接活。公共大厅有几张大桌子，工匠来了坐下就干，干完就走，桌子空出来给下一个人。

**这就是"计算层"——按需分配的工作空间。** 不再为每个人常驻一间房，而是共享一批弹性工位，来多少人开多少桌。

但新问题来了：工匠出门了，他们的图纸和记忆留在哪儿？

于是市长又做了第二件事：在市中心建了一座**档案馆**。

- **一楼是速记台**（热状态存储）：工匠干活时，每一步进展都飞速记在小纸条上，贴满一面墙。如果工匠中途被打断，第二天回来，看一眼墙上的纸条就能接着干。纸条用的是飞快能写的墨水，但只能保存几天。
- **二楼是档案室**（对话记录数据库）：任务完成后，整份记录归档进柜子，永久保存，随时可查。
- **三楼是联想库**（长期记忆向量库）：档案馆的管理员是个聪明人，他读完了所有档案后，会提取出一条条"经验"。当新工匠问"以前有没有人做过类似的事"，管理员能在几秒内从联想库里翻出相关的经验摘要。
- **地下室是货仓**（对象存储）：工匠的大件工具、用户送来的大箱子、做好的成品，全堆在这里。平时不动，但需要的时候可以搬上楼。

**这就是"存储层"——按数据类型分层的中央仓库。** 每一种数据有不同的"温度"，需要不同的存取速度和保存方式。

工匠们的工作流程变成了这样：

1. 来到公共大厅，坐下
2. 从二楼档案室取出自己的身份卡和性格说明书
3. 从地下室搬来需要的工具箱
4. 去三楼联想库查一查"以前做过什么类似的"
5. 在一楼速记台上铺开纸条，开始干活
6. 每一步进展都记在速记台纸条上
7. 交出成品，站起来
8. 不活跃的工具间被清空，东西搬回地下室

城市的成本骤降。不再需要十八栋楼的常驻工坊——只需要几张大桌子和一座档案馆。桌子的数量可以随客流伸缩：旺季加桌，淡季撤桌。

但新问题又来了：如果两个工匠同时服务同一个老客户，一个在修改方案，一个在回答咨询，他们可能同时去二楼调同一份档案——**谁先写谁后写？** 如果工匠 A 改了方案，工匠 B 还在用旧版本回答问题，老客户就会得到矛盾的信息。

市长叹了口气："分离容易，一致难。"

他请来了一个调度员（负载均衡），制定了规则：同一个客户的请求，始终路由到同一个工匠（sticky session）。如果那个工匠正在忙，宁可排队也不能找别人顶上——除非确认旧工匠已经彻底交差，档案封存完毕，才能换人接手。

智囊城的故事流传开来。远方有一座叫"克劳德庄园"的地方，也做了类似的事——他们把工匠的"对话日记"（Session）、"指挥室"（Harness）和"操作间"（Sandbox）拆成了三栋独立的楼，一模一样的道理，只不过他们更喜欢用学院派的术语来讲。

而那些还让工匠住在工坊里的城市，渐渐发现自己越来越扛不住——用户越多，空工坊越多，账面上的数字越难看。

市长最后总结了一句话：

> "当你的工匠开始比工坊多的时候，就别再给每个工匠一间房了。把房拆成桌子和档案馆，桌子按需摆，档案馆分层放。**存归存，算归算，能分就分。**"

---

## 💡 概念解析：Agent 存算分离（Compute-Storage Separation）

**Agent 存算分离**是将 Agent 运行时的"计算"和"存储"拆成独立层的架构模式，是 Agent 托管服务从原型走向规模化的关键设计。

**问题根源：** 存算一体的模式下，每个用户需要一个常驻容器（Pod），里面包含 workspace、提示词、skills、对话记录。即使 95% 的时间空闲，也在消耗内存和计算资源。真实案例：500 Pod 部署在 18 台服务器上，月成本 $5,000，而月收入仅 $8,000，利润极薄。

**核心设计：** 将四种不同访问模式的数据分配到不同的存储引擎——热状态用 Redis KV（毫秒级读写，断点恢复）、对话记录用 Postgres（结构化查询）、长期记忆用向量数据库（语义检索）、工作产物用 S3/OSS（大文件冷存储）。计算层则是无状态的 Pod，按需扩缩容。

**关键挑战：** 分布式场景下的数据一致性（同一 Agent 的状态可能同时存在于多个 Pod 和 KV 中）、冷启动延迟（每次请求需从远端存储加载上下文）、沙盒池管理的资源平衡。

这和 Anthropic 的 Managed Agents 架构（Session/Harness/Sandbox 三层解耦）解决的是同一个问题——从独占容器到共享计算的演进。理解了存算分离，就能看懂 Manus、Claude managed agents、Pi Agent 等所有规模化 Agent 服务的底层架构。
