# 刻刀与竹简

大梁国的记事官沈书，有个外人不知道的烦恼。

皇帝每天早朝，百官奏事，沈书负责把一切记录在案。他的工具很简单：一卷竹简，一把刻刀。竹简的长度是固定的——从宫里领的制式竹简，每卷恰好一千二百个字的位置。

大多数早朝，一千二百字绰绰有余。但有些日子——讨论边关战事、赈灾方案、税收改革——官员们你来我往，一个问题牵出三个问题，每个问题又引出一堆证据和反驳。沈书越记越快，手腕发酸，然后他抬头看了一眼竹简——

满了。

后面还有半场朝会没记呢。

---

沈书抬起头，望着还在激烈辩论的群臣，心里开始盘算。

他的第一个念头是：把最前面的话擦掉，给后面腾地方。但他立刻否决了。开朝时兵部侍郎说"北境粮草仅够两月"，这句话是后面所有讨论的前提。擦掉它，后面的记录就成了无根之木。

第二个念头：把所有记录精简一下，每句话只留关键词。但他试了一下——精简后的记录虽然短了，读起来却像鬼画符。"粮→不足→调→江南"——三个月后谁看得懂？何况有些对话特别长，有些又极短，按照"保留最近十句"来截断，有时候刚好丢了最重要的那一句。

他陷入沉思。

然后，沈书做了一个大胆的决定。

他拿出一张空白的绢帛——比竹简小得多，但可以写小字——开始写摘要：

> 兵部奏：北境粮草仅够两月，需从江南调拨。户部驳：江南漕运已满载秋粮。上命：工部勘察 alternate route。结果：走运河北段可行，需银十二万两。

这一小段绢帛，替代了竹简前半段几百字的原始记录。然后他把竹简擦干净，在开头粘上绢帛，后半段继续记当场朝会。

摘要归摘要，最近发生的几轮对话——原文一字不动。

效果不错。

---

但问题很快又出现了。

第二个月，一场关于盐税改革的大朝会。辩论持续了整整一天，沈书的竹简满了三次。他不得不压缩了三回。

第一次压缩很顺利。但第二次压缩时，他犯了错误——他从竹简最开头开始重新压缩，把第一张绢帛的摘要又压缩了一遍。

"摘要的摘要。"

沈书事后检查时出了一身冷汗。原始记录中，盐运使提到"两淮盐场年产量四百万引，但实际运出仅三百万，差额去向不明"。这句话在第一次压缩时保留了。但第二次压缩时，它被进一步简化成了"盐税有亏空"。

那个关键细节——"差额去向不明"——丢了。

从此沈书立下一条铁律：**第二次压缩从上一次留下的边界开始，绝不碰已经压缩过的绢帛。** 只处理第一次压缩之后新产生的内容。

---

还有一次更险。

那天的议题是河工修缮。工部提交了一份详细的河道勘察报告，然后提出了三套修缮方案，每套方案又有预算、工期、风险评估。沈书记到一半，竹简又满了。他开始压缩，刚好把工部的报告和方案比选拆开了——勘察报告的内容进了绢帛摘要，但三套方案的比选结果留在了竹简上。

后来皇帝翻看记录时问："为什么只有方案比选，没有勘察数据？工部说河底淤积三丈，你们是在三丈的基础上比选的，还是一丈的？"

群臣面面相觑。没有人知道答案，因为勘察数据和方案比选被拆开了。一个问题被剥夺了它的回答，剩下的部分比什么都没有更危险——它会让人以为已经掌握了全貌。

沈书挨了二十板子。然后他立下第二条铁律：**压缩时，永远不在一份奏报被回应之前把二者分开。提问和答复必须待在一起。**

---

还有一个小麻烦。有几天，某位大臣特别能说，一个人的一轮发言就占了竹简的三分之一——洋洋洒洒引经据典，还附了三份佐证材料。沈书想压缩，可这一轮发言实在太长，保留全文超了预算，整个丢掉又可惜。

他的解决办法是：把这一轮发言从中间劈开。前半段的引经据典压缩进绢帛，后半段的结论和佐证保留在竹简上。劈开的位置也有讲究——绝不会在一份佐证材料提到一半的时候切下去。

---

五年后，沈书的记事法成了大梁国史官的标准操作规程，被称为"沈氏缩简法"。核心六条：

一、按实际占用的简面空间判断是否需要压缩，不是按发言的次数——因为一句话可能占两个字，也可能占两百个字。

二、压缩时，旧记录缩成绢帛摘要，但最近的内容保持原样不动。

三、绝不在一份奏报被回应之前把二者分开。没有答案的问题是误导，比没有问题更危险。

四、遇到单次发言过长的情况，允许从中劈开，但劈开点必须落在完整的一问一答之后。

五、再次压缩时，从上次留下的边界开始，不碰已经压缩过的绢帛。摘要的摘要是不可接受的。

六、所有原始记录一律存入皇家档案馆，绝不销毁。绢帛摘要是给皇帝看的便利，不是真相本身。

后世史官评价：沈书最大的贡献不是发明了压缩方法，而是想清楚了一个根本问题——**压缩的目的不是让记录变短，而是让有限的竹简上，永远保持一个连贯的、可理解的当下。** 读记录的人不应该感觉到中断——从绢帛摘要到竹简原文的过渡，应该像一个人从回忆回到现实那样自然。

---

💡 概念解析：Agent 上下文压缩（Context Compaction）

这则寓言讲的是 AI Agent 的"上下文压缩"机制。当 Agent 处理长任务时，对话历史会不断增长，最终超出模型的上下文窗口容量。这时不能简单截断——前面提到的文件内容、代码结构、bug 根因可能正是后续推理的基础。

核心设计思想与寓言的对应：

- **竹简的固定长度** = 模型的上下文窗口（如 128K tokens）。触发压缩的依据是实际 token 占用量，而非消息条数——因为一条 `ls` 命令可能 50 tokens，一条 `read file` 结果可能 5000 tokens。

- **绢帛摘要 + 保留最近原文** = 压缩策略。旧消息被压缩成结构化摘要（包含文件读写记录等关键信息），但最近约 20K tokens 的原始对话保持不动。

- **不在奏报和回应之间切分** = Cut Point 规则。工具调用（toolCall）和工具结果（toolResult）是语义上不可分割的一对，拆开后模型会基于不完整信息做出错误推理。

- **劈开单次过长发言** = Split Turns。当单个 turn 超过保留预算时，允许从中切分，但切分点仍在完整的调用-响应对之后。

- **从上次边界开始二次压缩** = 避免摘要的摘要。第二次压缩只处理新累积的内容，不重新压缩已有的摘要。

- **皇家档案馆** = JSONL 日志文件。原始消息永不删除，只是不再送入模型。随时可以回溯、审计、调试。

这个机制来自 Pi Agent 的实现（由 Cell/cellinlab 教程拆解），代表了一种在工程可靠性和信息保留之间取得实用平衡的上下文管理策略。
