📖 每日工程寓言 — Vibe Coding

# 灵感建筑师

老梁是城里最有名的建筑设计师。他画一张蓝图要三个月，每一根梁的位置都反复验算。客户嫌慢，他就讲道理：「房子要住一百年，快不了的。」

后来城里来了一批新工匠。他们不看蓝图，客户说「我想要一个有阳光感的客厅」，工匠拿起工具就干。第一天搭出框架，第二天装好窗户，第三天就请你来验收。

老梁嗤之以鼻：「这不叫盖房子，这叫堆积木。」

但客户们蜂拥而去。因为新工匠三天就能让你看到一栋房子——虽然窗框有点歪，但阳光确实照进来了。不满意？拆了重来，反正只花了三天。

老梁的徒弟小陈也去试了。他跟一个叫阿灵的工匠合作，用一种新方法：他只管描述感觉。「我要一个让人走进去就想坐下来的书房。」阿灵点点头，开始干活。

两天后，书房真的出现了。书架的弧度很舒服，光线恰好落在阅读区。小陈第一次体会到一种全新的工作方式——他不再画图纸，不再计算承重，他只负责**品味**。说「要什么」，而不是「怎么做」。

但好景不长。

小陈接了一个大单子：一整栋办公楼。他像往常一样描述感觉，阿灵飞快地建造。第一层完美，第二层不错，第三层……楼梯对不上。不是阿灵的错——阿灵只能看到当前正在造的那一层，不知道第一层的楼梯从哪里拐弯。

小陈想了个办法：每建完一层，就让阿灵写一份「这层的东西放在哪」的记录。下一层开工前，先读记录。这办法起初很管用。

但到了第八层，记录已经写了几百页。阿灵开始犯迷糊，把第三层的电梯门开在了第五层的位置。小陈去查，发现第五层也有人写过类似的记录，但措辞不同，阿灵没认出来是同一件事。

大楼变成了一个**鬼屋**——每一层的改动都可能让另一层出问题，但没人知道是哪一层、哪个改动。小陈花了比盖楼更多的时间去修bug。

老梁听说后，走过来说了一段话：「五十年来我们这个行业，一直在跟错误做斗争。不是因为建筑师蠢，是因为复杂度会吃掉你的记忆。我的蓝图不是限制自由，是我**把判断力存进了纸里**。我不在的时候，图纸还在。」

小陈恍然大悟。问题不在阿灵——阿灵的手艺没问题。问题在于他只让阿灵**造**，没让阿灵**记住**。阿灵每干完一活儿，应该留下三样东西：**测试**——验证这一层没有塌；**文档**——记录为什么楼梯从这里拐弯；**评估**——确认这层的质量不低于上一层。

有了这三样东西，质量就只会往上涨，不会往下跌。就像一个**棘轮**——只能往前转，不能往后退。下一任工匠接手时，测试会阻止他拆掉承重墙，文档会告诉他为什么墙在这里，评估会告诉他这栋楼目前的水平在哪里。

小陈回去重新来过。这次，阿灵每造完一层，都会自动写测试、写文档、跑评估。到了第八层，楼梯没有再对不上。到了第十五层，整栋楼稳如磐石。

而小陈的工作，从「画三个月的蓝图」变成了「每层花十分钟品鉴，说一句『这个转角不对，要更圆润』」。

**代码的生产成本趋近于零之后，真正稀缺的不再是实现能力，而是判断力和品味。**

💡 **概念解析：Vibe Coding**

Vibe Coding 是一种用自然语言描述意图、让 AI 编码代理快速构建软件的工作方式。它的核心哲学是「速度优于完美」——先让东西跑起来，再迭代优化。开发者不再手写代码，而是像产品经理一样表达需求，AI 负责实现。

这个概念之所以在 2026 年爆发，是因为 coding agent 的能力越过了「奇点」：原来需要 100 天开发的软件，现在 1 天就能完成。当代码的生产成本趋近于零，稀缺资源就从「实现能力」转移到了「判断力、品味和组合能力」。

但 Vibe Coding 有一个致命陷阱：**跳过测试、文档和评估**。没有这些「棘轮」机制，代码库很快会变成一个「鬼屋」——每次改动都可能在意想不到的地方引发问题。Garry Tan 的总结一针见血：「AI 编码没问题，他们只是没装棘轮。」

成熟的 Vibe Coding 流程会在每次迭代中自动积累测试覆盖、决策文档和质量基线，形成**只升不降的质量地板**。这不是限制自由，而是把判断力持久化——让下一轮 AI 代理站在上一轮的肩膀上，而不是在废墟里重新开始。
