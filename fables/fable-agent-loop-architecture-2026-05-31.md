📖 每日工程寓言 — Agent Loop

---

在一座古老的王城里，有一位名叫陆衡的年轻官员。

陆衡刚刚被任命为"御前顾问"——一个听起来很威风的头衔，但他很快发现，这活儿比想象中复杂得多。

他的工作是替国王解决问题。但国王从不把问题说清楚。

"城东的水渠堵了。"国王的第一道旨意就这么一句话。

陆衡是个聪明人，他很快想到了方案：派工部的人去疏通。于是他写下文书，盖上官印，交给驿卒。

驿卒跑了一个时辰，带回了工部的回信："水渠无碍，是上游水坝闸门卡住了。"

陆衡恍然大悟，重新整理情况，再次写下应对方案——派水务司的人去修闸门。

驿卒又跑了一个时辰。水务司回信："闸门正常，是河床淤泥堆积导致水位过高。"

陆衡咬牙，第三次提笔——调清淤队。

驿卒再跑。清淤队回信："已清完，但清淤过程中发现一段渠壁有裂缝，建议同时修补。"

陆衡第四次提笔。这一次他写了两件事：确认清淤成果，同时派修缮队加固渠壁。

两支队伍同时出发。修缮队先回来了："渠壁加固完毕。"清淤队也回来了："淤泥已清，水位恢复正常。"

陆衡终于松了口气，把完整结果呈报给国王。

---

他把这段经历讲给同僚听。同僚笑着说："你这不就是个传话的？有什么难的？"

陆衡摇了摇头。"传话是最容易的部分。难的是——你要记住之前每一次往来的结果。每一次回信，都要和之前的所有信息拼在一起，才能做出下一步判断。有一次，水务司的回信晚到了半天，我差点基于不完整的信息做出错误决策。"

"还有更难的，"他压低声音，"国王有时候会在你做事做到一半的时候，突然又下第二道旨意。比如上次，我正在派清淤队，国王突然说'顺便查查城西的粮仓够不够吃三个月'。你不能放下手里的活儿不管，但也不能无视国王的新命令。我得等清淤队回来，把两件事的结果一起整理好，再分别处理。"

同僚愣住了。"那……你怎么决定先处理哪件事？"

"规矩很简单，"陆衡说，"手里正在做的，做完为止。做完之后再看有没有新吩咐。新吩咐会在下一轮开始时一起处理。"

---

陆衡的名声越来越大，因为他处理问题的模式非常可靠。

别的顾问有各种毛病：有的做完一件事就停了，等国王再开口；有的一次性把所有消息混在一起，分不清哪些是旧结果、哪些是新指令；有的接到消息直接冲出去执行，连方案都没想好就跑。

陆衡和别人最大的区别，是他在书桌上划了一条线。

线的左边，是他自己——一个只负责思考、记录和下令的角色。他不亲自去疏通水渠，不亲自去量粮仓。他只做一件事：根据当前掌握的所有信息，决定下一步该做什么。

线的右边，是驿卒和各部官员——负责跑腿和实际干活的人。他们只管接令和回报，不管陆衡为什么这么决定。

这条线的好处，陆衡后来才完全想明白：如果有一天驿卒换了人，陆衡的工作不受影响；如果国王换了人，陆衡的工作流程也不需要改。他自己的思考方式——收到信息、整合上下文、决定下一步——是稳定的、可复用的。

后来，陆衡把这个方法写成了手册，取名《顾问循环》。

手册的第一句话是：**好的顾问不是最聪明的，而是循环最稳的。**

---

💡 概念解析：Agent Loop（Agent 循环架构）

Agent Loop 是 AI Agent 系统的核心运行时闭环。它不是一个一次性的大模型调用，而是一条围绕 LLM 构建的**持续控制流**：接收上下文 → 请求模型推理 → 模型输出工具调用 → 执行工具 → 把结果拼回上下文 → 再请求模型……直到模型判断任务完成、不再发起工具调用为止。

Pi Agent 的工程实践揭示了几个关键设计：

**双层循环**：内层循环处理工具调用（"做完手里的事"），外层循环检查 follow-up 队列（"看有没有新吩咐"）。中间的 steering 机制允许用户在 Agent 工作中途改变方向，但不会打断正在执行的原子操作——就像陆衡等清淤队回来后才处理国王的新旨意。

**状态机**：Agent 有严格的 Idle → Streaming → ExecutingTools → Aborted 状态转换，每个状态都有明确的进出条件，防止重入和竞态。

**副作用边界**：Agent Loop 本身不碰磁盘、不直接执行操作，只负责状态转换和决策。真正的副作用（写文件、跑命令）发生在工具层，可以被 hook、权限和校验拦截。这就是陆衡桌上那条"线"——思考归思考，执行归执行。

这个架构的核心洞察是：**大模型供应商会换，工具会变，UI 会变，但 Agent Loop 的本质——"收到信息、整合上下文、决定下一步"——相对稳定。** 把稳定的核心和不稳定的外围分开，每一层可以独立演进和测试。
