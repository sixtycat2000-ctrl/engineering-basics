# 提名接力

长风城被困了三个月。

城外大军压境，城内粮草告急。太守张伯庸坐在议事厅里，面前是一张巨大的任务表。

"张弓——东门守军再调五百人。"

"李匠——城墙裂缝今晚必须补上。"

"赵厨——军粮配给减三成。"

"钱探——派人去查敌营补给线。"

他一条条念，一条条分。每条指令经过三道传令兵，再落实到人。分完一百二十条指令需要一整天。而第二天，又有新的指令要分。

张伯庸很累。但他觉得这就是指挥——一个人把所有任务理清楚，分给该做的人。

直到有一天，城外突然起雾，探子来报：敌军趁大雾正在调动，方向不明。

张伯庸看着手里的任务表，愣住了。他不知道该把这条消息给谁。给张弓？他守东门，管不了全局。给钱探？他只管侦察补给线。给赵厨？

"谁管雾天防御？"他问。

没人回答。因为任务表里没有这一项。

---

与此同时，在城东的酒馆里，一群老兵在喝酒。

传令兵跑进来喊："太守有令——东门增兵五百！"

张弓放下酒碗，接过令箭，带着人走了。

但张弓走了之后，酒馆里还坐着两个人——工匠老李和斥候小钱。老李本来是来跟张弓商量城墙加固的，小钱本来是来给张弓送最新情报的。

他们面面相觑。

"张弓走了，"老李说，"城墙的事我问谁？"

"我也没法交情报了，"小钱说。

三个人本来可以互相通气——张弓知道兵力部署，老李知道城墙弱点，小钱知道敌军动向。但指令只点名了张弓，另外两个人的信息链条就断了。

老李叹了口气："我们三个人，其实需要同时在场才能把事情想清楚。但太守每次只叫一个人。"

---

新的太守叫沈不言。

沈不言上任第一天，做了一件奇怪的事——他在城墙四角各挂了一块铜牌，上面写着同样的规则：

> **铜牌令：见事提人。**
>
> 城中任何人发现紧急事务，在大声通报时必须"提名"一个名字。被提名的人听到自己的名字后，自动负责接手此事，可以再提名下一个人。
>
> 例："@张弓 东门发现异动！"@张弓 听到后立即赶到东门。若需支援，张弓可再喊："@老李 东门墙根开裂需要加固！"
>
> 不需要等太守下令。不需要传令兵。听到名字就是命令。

铜牌挂出去的第一天，什么也没发生。大家都等着看沈不言怎么指挥。

第二天夜里，起雾了。

城北巡逻的小兵看到了雾中的动静，他没有跑去找太守，而是站在原地大喊了一声：

"@钱探！城北雾中发现火把移动方向——向南！"

钱探恰好就在三百步外巡逻。他听到了自己的名字，立刻改变路线，向城北跑去。同时他边跑边喊：

"@张弓！钱探已确认——敌军火把从城北向南移动，可能在合围东门！"

张弓在东门听到自己的名字。他不需要等太守确认，直接下令把东门预备队调上城墙。

张弓又喊了一句："@老李！东门城墙可能要承受冲击，检查所有裂缝！"

老李在东门内侧补墙。他听到了，放下灰桶，拿上工具开始排查。

从发现火把到东门备战，不到一炷香的时间。没有传令兵，没有任务表，没有太守的指令。

沈不言从头到尾坐在太守府喝茶。

---

张伯庸不服。

"那不就是乱喊吗？万一没人听到呢？万一喊错了人呢？万一两个人同时被提名呢？"

沈不言说："你的任务表能处理'雾天敌军方向不明'吗？"

张伯庸沉默了。

"你的方法，"沈不言说，"是所有事情都经过一个人——你。你知道每个人该做什么，但前提是你必须提前想清楚所有可能的情况。城外起雾这种事，你的任务表里没有。"

"那你的方法呢？"

"我不提前想清楚所有情况。我把'谁该处理这件事'的决定权，交给现场的人。他看到雾中动静，他最清楚这个信息该给谁——给侦察兵，而不是给厨子。侦察兵收到信息，他也最清楚下一步该通知谁——给守门将军，而不是给工匠。每个人只做他最擅长判断的那一步。"

"但如果喊错了人呢？"

"被喊的人如果发现自己处理不了，他可以再喊。提名不是终审判决，是接力棒。接不住就传下去，总有人接得住。"

---

沈不言后来还补了一条规则：

被提名的人接手处理之后，会把处理结果刻在城墙内侧的一块石板上。这些石板按日期排列，任何人路过都能看到。

"不需要记档官。每个人处理完自己的事，自己写一条记录。下次再遇到类似的事，任何人都能翻石板看看上次怎么处理的。"

张弓有一次翻石板，看到三个月前老李写的一条记录："六月三日，暴雨冲刷东门墙基，用三尺木桩加固，间距一丈。"

第二天，当又有暴雨预报时，张弓没有去问太守，直接提名了老李。

---

三个月后，长风城解围了。

解围那天，沈不言站在城墙上，看着底下忙碌的士兵们。没人喊他的名字。没人等他的命令。每个人都在自己该在的位置上，做着该做的事。

有人在喊："@赵厨 南门伤兵二十人需要热汤！"
有人在喊："@老李 西门城墙被撞了一次，检查结构！"

沈不言忽然明白了：一个好的指挥官不是分任务的人。好的指挥官是设计那块铜牌的人。

---

## 💡 概念解析：消息路由与提名协调（Mention-Driven Routing）

在多 Agent 系统中，如何让多个专业 Agent 协作完成任务，是一个核心工程问题。

**传统方式——中央调度（Central Orchestration）**：一个中央调度器（或编排器）预先定义好工作流——第一步由 A 做，第二步由 B 做，第三步由 C 做。所有任务流经调度器，调度器负责分派和串联。就像张伯庸的任务表和传令兵。这种方式简单清晰，但有两个致命弱点：第一，调度器必须预判所有可能的情况，无法处理意外；第二，调度器本身是瓶颈——所有信息都要经过它，它一卡，全系统卡住。

**消息路由方式——提名驱动（Mention-Driven Routing）**：系统中的每个 Agent 都有自己的名字（身份标识）。Agent 之间通过"提名"（@mention）来协调——谁发现了问题，谁就提名最合适的人去处理；被提名的人处理完后，如果需要，再提名下一个人。不需要中央调度器预先编排，也不需要传令兵中转。就像铜牌令——现场的人最清楚信息该给谁。

Slark（开源 AI 团队操作系统）就是这种模式的工程实现：用户在对话中 `@Architect`，Architect Agent 自动接手设计任务；Architect 设计完方案后，在输出中 `@Dev`，Dev Agent 自动接手编码。每个 Agent 自主决定是否需要提名下一个 Agent，以及提名谁。不需要硬编码的流程图，也不需要中央编排器。

这种模式在工程领域并不陌生——微服务中的消息队列和事件驱动架构，Unix 管道中的进程间通信，甚至 Git 中"谁被 @ 了就谁来 review"的代码审查流程，本质上都是同一件事：**用消息（提名）代替调度（指令），让最接近问题的人做路由决策。**

关键设计原则：
1. **身份即接口**：每个参与者有明确的名字和职责，被提名就意味着被授权。
2. **现场决策权**：谁在现场，谁决定下一步该提名谁——不要远程调度。
3. **消息即日志**：所有提名和处理结果都留下记录，形成组织记忆。
4. **允许转发**：被提名的人如果处理不了，可以再提名更合适的人——消息是接力棒，不是终审判决。

这就是为什么 Slark 的核心理念是"你设定 Goal，AI 自动配备 Team"——Goal 定义终点，@mention 定义接力过程，整个团队在消息流动中自组织完成工作。
