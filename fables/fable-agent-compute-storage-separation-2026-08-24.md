王国里有一位精明的商人，叫老陈。他经营着全国最大的"私人管家"服务——每户贵族只要付一笔年费，就配一个专属管家，全天候待命。

老陈的商业模式很简单：给每位客户安排一个独立的宅院，管家住在里面，客户的衣服、账本、食谱、家训全部存放在管家自己的房间里。管家的日常工作就是坐在院子里等指令，收到后翻阅资料、执行任务、交付结果。

生意很好，很快有了五百位客户。老陈一口气租了十八座大宅子，每座宅子安置二十多位管家。每月光房租就五千金币。

但问题慢慢浮现了。

老陈的账房先生偷偷做了一次统计，结果让他倒吸一口凉气：五百位管家，平均每天只有两小时在干活。其余二十二小时，他们坐在空荡荡的院子里喝茶、发呆、等下一位主人召唤。但宅子的租金一分不减少——无论管家是在拼命干活还是在打瞌睡，那间房、那块地、那份口粮，都实打实地消耗着。

更荒谬的是，每位管家的房间里堆满了资料，但其中九成的时间，那些资料根本没人翻。一位管家的衣服账本可能连续三个月无人问津，但它仍然占据着最贵的地段——宅院的正房。

"我们是在为空气付房租。"账房先生把报表拍在桌上。

老陈苦思冥想。他想过裁人，但客户要求的是全天候响应，管少了来不及。他想过让管家兼任多家，但管家们习惯了在自己的房间里找东西，换个环境就手足无措，经常拿错账本、认错主人。

转机来自一次意外的火灾。

那天夜里，三号宅院走水。火不大，但烧掉了一位管家房间里所有的资料——衣服尺寸、家训、食谱，全没了。老陈急得跳脚，连夜赶去慰问。到了现场他发现一件奇怪的事：管家并没有崩溃。他正坐在废墟旁，有条不紊地从旁边的公共档案阁里翻出备份，然后借了隔壁宅院的厨房，照样给主人备好了早餐。

"你的资料不是都烧了吗？"老陈问。

管家指了指街对面的档案阁："备份都在那儿。我只需要脑子——脑子没烧。"

老陈愣在原地，那句话像一道闪电劈开了他的天灵盖。

他连夜召集建筑师，画了一张新图。

**不再给每位管家一间宅院。** 取而代之的是：

街中心建一座巨大的**公共档案馆**——分四个区域。一楼是**快件柜**，放管家工作到一半的备忘和进度条，随时取放；二楼是**档案室**，存每一户的对话记录和任务日志，整整齐齐排满书架；三楼是**回忆阁**，按照意思相近的程度把过去的经验归类，管家不用从头翻，说个大概就能找到；地下室是**大货仓**，存客户的衣物、文件、工具箱等大件，用的时候才搬。

街对面只设一个**公共办事大厅**——几张桌子、几支笔、几部电话。管家们不再有专属房间，他们像轮班的店员一样，谁有空谁来。接到任务时，从档案馆调取资料，在桌上摊开干活，做完把结果和更新后的资料放回档案馆，桌清人走，下一位管家可以立刻坐下来服务另一位客户。

建筑师问老陈："那管家换人的时候，会不会找不到东西？"

"不会。"老陈指了指档案馆的四个区域，"资料不属于任何一个管家，它属于客户。任何一位管家走进来，只要知道客户的名字，就能从同一个档案馆里调出完全一样的资料。脑子是管家的，记忆是档案馆的。"

改革后的第一个月，老陈把十八座宅院退租了十五座。只留三座办事大厅，轮班安排管家。月租从五千金币骤降到不足一千。客户体验没变——他们依然随时召唤、随时响应，甚至更快了，因为不再需要等"自己的管家"从午睡中醒来，任何一个清醒的管家都能接单。

但老陈也发现了一个新麻烦。

有一天，客户张老爷同时派了两个任务，两个不同的管家分别接了单。甲管家在档案室里更新了张老爷的偏好记录，乙管家还不知道，继续按旧版本执行。张老爷收到了一份已经不想要的菜谱和一份刚修改过的出行计划，气得拍桌子。

"记忆在档案馆里，但管家的手伸进档案室的时候，**谁先谁后、谁改了什么，没人管。**"账房先生一针见血。

老陈在档案馆门口加了一把锁和一本登记簿。同一时间，一位客户的档案只允许一位管家进入修改。其他人可以看，但不能动。等前一位管家退出，锁才打开。

这又引出了第二个问题：乙管家等锁的时候闲着，白白浪费了计算能力。老陈开始研究怎么让等待的管家先去服务其他客户，而不是傻站着。

"这件事没有尽头。"老陈坐在只剩三座大厅的街上，望着来来往往的管家们，"你解决一个问题，就会暴露下一个。但至少——"他看了看账本上骤降的数字，"我们不再为空气付房租了。"

---

💡 **概念解析：Agent 存算分离（Compute-Storage Separation）**

传统 Agent 托管采用"存算一体"架构——每个用户独占一个 Pod，提示词、技能、对话记录全部打包在容器内。就像老陈给每位客户配专属宅院。这种模式下，即使 Agent 95% 的时间空闲，Pod 的内存和计算资源也在持续消耗。500 个常驻 Pod 月成本 $5,000，利润被基础设施吃掉大半。

存算分离的核心思想是：**把"计算"（Agent Loop 的推理、工具调用）和"存储"（提示词、记忆、对话记录、工作产物）拆成独立的层。** 计算层用无状态 Pod 池按需调度，存储层按数据访问模式分成四级——热状态用 Redis KV（毫秒级，断点恢复）、对话记录用 Postgres（结构化查询）、长期记忆用向量数据库（语义检索）、工作产物用对象存储 S3/OSS（大文件冷热分离）。任何计算节点接到请求后，从统一的存储层拉取上下文，执行完再写回，自身不持有任何状态。

代价是**冷启动延迟**（每次都要从远端存储加载上下文）和**数据一致性**（多副本并发修改同一状态需要锁和负载均衡策略）。但换来的是资源利用率数量级的提升——从"每人一座宅院"到"共享办事大厅"，这是 Agent 服务从原型走向规模化的必经之路。
