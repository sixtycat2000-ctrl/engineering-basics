# 一支笔和一本簿子

晋商老范家有个规矩，传了三代——每个出师的账房先生，必须把所有商路的数据倒背如流。

五十二条商路，每条路十几个关键数字：里程、驿站、关税、汇率、运输时限。客人一进门就问"一百两银子汇到迪化要多少费用"，你得张口就答。翻书？翻书就不是合格的账房。

老规矩在五条路的时候运转良好。二十条路的时候，学徒要多背半年。到了五十二条路，说明牌铺开占满了三张八仙桌，光读完一遍就要一上午。去年新开了三条路，两个老账房辞了——不是跳槽，是真背不动了。

新来的学徒叫小赵，瘦瘦小小，话不多。上头给他发了背诵任务单，他看了一眼，说："掌柜的，我不背。"

大掌柜老孙的胡子气得一翘一翘："不背？你——"

"给我两样东西就行。"小赵不慌不忙，伸出两根手指，"一本商路簿子，一支笔。"

账房里炸了锅。老师傅老马第一个跳出来："开票号又不是开书院！客人等着呢，你翻簿子翻到天黑？"

小赵没争辩。他打开空簿子，从第一页开始，把五十二条商路的说明牌内容原原本本抄了进去。然后他把那三桌子说明牌全收了。

第二天，第一个客人来了。

"一百两银子汇到西安，走北路。"

老马已经在脑子里把五十二条路的数字过了一遍——先得排除不相关的南路、东路数据，再定位到西安北路的那一组……正在翻腾，小赵已经翻开了簿子。

他不是从头翻到尾。他直接翻到标着"西安"的页，用笔写了一个小算式——里程数、关税率、汇率，三个数字，一乘一加。

"四两五钱，三日内到。"

比老马快了半拍。

老马不服气："简单路线碰巧而已。来个复杂的——这位客人要从苏州运丝绸到迪化，经西安中转，又要汇银又要带货。你翻簿子翻得过来？"

小赵拿起笔，在纸上写了三行：

"第一步：查苏州到西安，丝绸运价。"
"第二步：查西安到迪化，驼运价。"
"第三步：查西安分号，当日汇率。"

他先翻到苏州那几页，找到丝绸运价——每匹三钱。再翻到迪化那几页，驼运费——每匹二两一钱。再翻到西安分号当日牌价。三个数字串在一起，总报价出来了。

不到一盏茶。

而老马还在把五十二条路的数字搅来搅去，同时还要排除从苏州直接到迪化的那条废路线——那路线两年前就停了，但他脑子里还记着，搅在一起分不开。

消息传遍了平遥城。隔壁票号的大掌柜来取经，看见小赵的簿子，皱眉头："这不就是偷懒？我手下账房可是正儿八经背了三年。"

小赵放下笔，问了一个问题："大掌柜，五十二条路，您的人背了三年。明年再开五十二条呢？再开五十二条呢？"

"那你翻簿子不也得花时间？"

"我花的时间是固定的。查三次，算一次。不管五十二条还是五百条，我的步骤一样多。但您的人每多一条路，就要多背一组数字。去年开了三条新路——您不就丢了两个账房？"

来人沉默了。

小赵继续说："而且您的人背了三年才出师，这三年什么都干不了。我不需要背，今天来了明天就能干活。新路线开通，当场就能报价——写进簿子就行。"

老孙站在门帘后面，全听见了。那天晚上，票号立了新规矩：账房不再背商路数据。取而代之的，是一本统一的商路簿，和一个标准的查算流程。每个账房只需要掌握两件事——**怎么查**，**怎么算**。

三年后，老范家的票号扩展到二百多条商路，遍及十八省。账房人数，一个没增加。而隔壁那个坚持背书的票号，在第一百条路的时候，关了门。

## 💡 概念解析：Code Mode（代码模式）

这个故事讲的是 Cloudflare 在企业级 MCP（Model Context Protocol）架构中提出的 **Code Mode**。

当 AI 智能体需要使用工具时，标准做法是把每个工具的完整定义——名称、参数、功能描述——全部加载到上下文窗口里。就像账房先生必须背下所有商路数据。4 个 MCP 服务器提供了 52 个工具，约占 9,400 个 token。每新增一个服务器，token 数量线性增长。

Code Mode 的思路是：**不预加载所有工具定义，只提供两个"元工具"**。一个用来搜索（`portal_codemode_search`，相当于故事里的"簿子"），一个用来执行（`portal_codemode_execute`，相当于"笔"）。模型通过编写 JavaScript 代码来动态查找工具、链式调用多个操作。

效果：52 个工具 → 2 个工具，约 9,400 token → 约 600 token，**减少 94%**。更关键的是成本固定——无论再接入多少服务器，始终只有 2 个工具定义。正如小赵所说："一百条、五百条，对我来说一样。"

这是经典的工程模式：**用"按需查找"替代"全量预载"**。人类记忆如此，软件架构如此，AI 工具系统也如此。不要把所有信息塞进有限的空间，而是提供高效的查询与执行接口——让使用者需要什么找什么。
