📖 每日工程寓言 — Agent 扩展系统

---

长安城里有一座朝廷。

朝廷的核心只有一个人：决策官老陈。老陈每天的工作非常纯粹——坐在案前，根据手里的卷宗，想出对策，写下来，交给下面的人去执行。执行的人回来了，带回新的卷宗，老陈再想，再写，再派。周而复始。

老陈非常擅长这个。他脑子清楚，判断准确，手也快。朝廷上上下下都佩服他。

但朝廷不止老陈一个人。

---

最早来的是一个叫赵全的御史。赵全说："最近总有奸细混进公文，你得在收到卷宗的时候先过一遍，把可疑的挑出来。"

老陈觉得有理，就照做了。从此他每天多了一道工序：收卷宗之前先过滤一遍。

后来又来了一个叫钱方的后勤官。钱方说："你每次写完对策，都不记得之前写过什么。我帮你建个档案室，把所有往来记录都存起来。"

老陈又觉得有理，于是他每次派人出去之前，先抄一份存档案。

再后来，工部尚书孙铁来了："你派出去的人，有时候会乱跑。我得在他们出发之前检查一下路线，确认他们不是要去烧皇宫。"

老陈点点头，又加了一道审批。

再再后来，孙铁又来了："光出发前检查不够，他们带回来的东西也可能有问题——比如带回了一封敌国的信。你得在他们回来的时候也检查一遍。"

老陈又点头。

再再再后来，户部侍郎周密来了："你案头的卷宗越堆越多，总有一天堆不下。我帮你定期整理，把旧的卷宗压缩成摘要，腾出空间。"

老陈说好。

---

三年后，老陈觉得自己快疯了。

他本来只想安安静静地想对策、写文书。但现在他每天的工作变成了：

收到卷宗 → 赵全过滤 → 周密检查有没有超量 → 钱方存档 → 孙铁审批路线 → 写文书 → 钱方再存档 → 孙铁检查回报 → 周密压缩旧卷宗 → 赵全过滤回报内容 → 想下一步……

每一环都是合理的，每一环都有人需要。但老陈发现自己已经没时间想对策了——他全部的精力都花在协调这些检查流程上。

更糟糕的是，赵全生病的时候，老陈得自己干过滤的活。孙铁出差的时候，审批流程就断了。而且每一次新增流程，都得改老陈的工作手册——因为所有的流程都是老陈在脑子里跑的。

老陈终于忍无可忍，去找丞相。

---

丞相听完，笑了笑。

"你知道问题在哪吗？"丞相说，"不是这些流程有问题，是你把它们全塞进了你自己的脑子里。"

他拿出一块木板，上面画了六个格子。

"你看，朝廷的核心是你——想对策、写文书。这是你的本职，不应该被其他事情干扰。但其他部门的需求也是真实的。所以，我们把你的工作流画出来，在这些格子之间留出插槽。"

丞相指着木板：

```
卷宗进来 → [格一] → 开始工作 → [格二] → 写文书/派人
→ [格三] → 执行 → [格四] → 回报 → 继续循环...
→ 卷宗太多 → [格五] → 整理
```

"每个格子就是一个插槽。赵全想过滤卷宗？他在格一注册就行。孙铁想审批？他在格三注册。钱方想存档？他在格四注册。周密想整理？他在格五注册。"

老陈问："那我怎么办？"

丞相说："你什么都不用管。每个格子里有人就执行，没人就跳过。你甚至不需要知道谁注册了什么——你只管想你的对策。"

"那谁来管这些格子？"

"不需要人管。格子是空的位子，各部自己登记、自己负责。哪天赵全走了，格一自然就空了，不影响你工作。哪天来了一位新的钱方，在格四一登记，你就多了一个存档的帮手。"

老陈沉默了很久，然后说："那我岂不是成了一个……纯粹只负责想对策的人？"

"对，"丞相说，"这才是一个好的决策官。"

---

三个月后，朝廷变了。

老陈只负责想对策和写文书，效率极高。六个格子里分别坐着赵全、钱方、孙铁等人，各司其职。新来的部门——比如负责翻译外文卷宗的翻译官——只需要在格二登记就行，不需要改动老陈的工作方式。

有一天，丞相来视察。他问老陈："你还能不能独立工作？"

老陈犹豫了一下，然后让人把六个格子的人都请出去。他发现——自己依然可以正常工作。只是没有过滤、没有存档、没有审批。效率可能不如以前高，但核心流程完全不受影响。

丞相满意地点头。"这就是这条设计最大的好处——你永远可以把自己剥离出来，验证你的核心能力是否还在。如果一切正常，那说明你的架构是对的。"

---

💡 概念解析：Agent 扩展系统（Extension System & Lifecycle Hooks）

Agent 扩展系统的核心问题是：**AI Agent 的核心循环（推理→工具调用→结果回传→再推理）应该是稳定且纯粹的控制流，但现实中的产品需求——权限审批、输入过滤、输出脱敏、状态持久化、上下文压缩——都在不断增加。把这些需求硬编码进 Agent Loop，就像把赵全、孙铁、钱方的检查流程塞进老陈脑子里一样，短期快，长期会让核心循环不可测试、不可维护。**

Pi Agent 的解决方案是在 Agent 生命周期的六个关键节点设置 hook（插槽）：`input`（输入进入时）、`before_agent_start`（循环开始前）、`before_provider_request`（每次 LLM 请求前）、`tool_call`（工具执行前）、`tool_result`（工具执行后）、`session_before_compact`（上下文压缩前）。每个扩展只注册自己关心的插槽，核心循环不知道也不需要知道有哪些扩展存在。

这本质上是**依赖反转**（Dependency Inversion）：核心定义接口（hook 点），扩展提供实现。好处有三：①核心循环可以独立单元测试——mock 掉所有扩展即可；②新增产品需求不需要改核心代码，只需写新扩展；③扩展可以独立开发和替换，不影响其他部分。与 Express 中间件、浏览器事件监听、数据库 trigger 是同一设计家族——在稳定的主干上，通过插槽机制承载不稳定的枝叶。
