# 身份与舞台解耦 — 一则寓言

星城有七座戏院，每座戏院风格不同。

东院的舞台擅长唱念做打，西院精通即兴话剧，南院专演哑剧，北院搞实验先锋。每座戏院各有自己的后台规矩、道具仓库、灯光系统，甚至演员的化妆间都不一样。

老莫是星城最有名的巡演经纪人。他手底下管理着三十多个演员，每个演员都有自己擅长的角色——有人演将军，有人演书生，有人专演丑角。

但老莫有一件烦心事。

每次派演员去新戏院，都得"重建"一遍。去东院之前，要帮将军演员重新整理戏服、重新背台词、重新适应东院的后台规矩——虽然他演的还是将军，角色没变，但换一个戏院就像换了一条命。更麻烦的是，如果将军演员在东院演了三天，积累了"东院版的将军经验"，一旦调去西院演同一个角色，所有经验全丢了——西院的后台是空的，一切从零开始。

演员们怨声载道："我是将军啊，换一座戏院我就不认识自己了？"

老莫试过很多办法。他让演员们背着自己的剧本转场——但不同戏院的剧本格式不兼容。他让化妆师跟班——但每座戏院禁止外来化妆师进入后台。他甚至试过让将军同时待在两个戏院——但演员只有一个身体，分身乏术。

问题归根到底只有一个：**戏院把演员的身份和自己的场地绑死了。**

一个演员之所以是"将军"，不取决于他站在哪个舞台上，而取决于他自己记住的台词、理解的角色的性格、拿手的那段亮相。这些东西是演员自带的，不是戏院给的。但星城的七座戏院偏偏不这么想——它们认定"来我这里的演员，就必须从我的后台重新出发"。

直到有一天，一个叫路桥的年轻女人来到星城。

路桥以前不是干戏的，她是修桥的。她看了一眼星城的巡演乱象，说了一句让所有戏院经理都沉默的话：

"你们修的是剧院，不是牢房。一个演员的身份凭什么被锁在你们的后台里？"

她提出了一个简单的方案：

**建一张通行证系统。**

每个演员领一张"身份卡"，上面写着：名字、擅长角色、台词储备、授权范围（比如"允许持剑"或"禁止高空"）。这张卡不归任何戏院管，而是由一个中立的巡演办公室签发。

当老莫派将军去东院，东院不再要求将军从零开始——它只需要读取通行证，就知道这位演员是谁、能演什么、有什么权限。将军在东院积累的演出笔记、学到的即兴台词，全存在通行证上，走到哪带到哪。

调去西院时也一样——西院读取同一张通行证，将军还是那个将军，只是换了个舞台。

演员们终于不用每换一座戏院就"失忆"一次。戏院也不必为每位来客准备全套的后台——通行证上已经写明了一切。

路桥给这个系统取了个名字：**路由**——不是把演员变成戏院的附属品，而是让演员的身份独立于任何一座戏院，在需要的时候被"路由"到最合适的舞台。

老莫站在东院的观众席上，看着将军在台上亮出那杆熟悉的银枪。他知道，这杆枪不是东院给的——是将军自己带的。

而这份从容，是过去十年里老莫从未见过的。

💡 **概念解析：Agent 身份与运行时解耦（Agent Identity/Runtime Decoupling）**

这个故事的核心来自 AgentSpace 的 **AgentRouter** 机制——将 Agent 的身份（角色、权限、知识、上下文）与其运行时执行环境（Claude Code、Codex、Hermes、OpenClaw 等）解耦。

在传统模式下，Agent 的身份和执行环境是绑定的：换一个 CLI 工具，就需要重新配置角色、重新加载上下文、重新设置权限。就像故事里"换戏院就得重建演员"——Agent 的价值被锁死在特定 runtime 的后台里。

AgentRouter 的解法是引入一个中立的"身份层"：

1. **身份独立**：Agent 的角色定义、技能、知识库、权限策略不归任何 runtime 所有，而是由统一的 workspace 管理
2. **运行时无关路由**：同一个 Agent 可以被路由到不同 runtime 执行，无需重建身份——通行证走到哪带到哪
3. **经验持久化**：Agent 在一次执行中积累的上下文和经验不会因为换 runtime 而丢失

这不是一个产品功能的问题，而是一个架构原则：**身份应该是一等公民，运行时只是执行通道。** 当你把这两层分开，Agent 才能真正成为"队友"而非"工具"。
